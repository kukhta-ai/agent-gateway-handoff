## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Give runtime users and their agents an executable flow for discovering available providers, understanding defaults, and choosing capsule providers for a session.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A runtime consumption flow is documented and executable for listing and inspecting available capsule provider capabilities by provider family and provider id.
- [ ] #2 Runtime users can see the selected default provider for each popular user-facing capsule layer, the source of that default, and any evidence or compatibility condition affecting it.
- [ ] #3 Runtime capsule provider overrides are accepted only for capsule provider families and cannot accidentally change AuthProvider, ChannelAdapter, or SecretStore deployment selection.
- [ ] #4 Runtime diagnostics distinguish unavailable, not installed, incompatible, evidence-missing, and ambiguous-default outcomes in terms a user or runtime agent can act on.
- [ ] #5 Runtime UX docs do not name CLI commands or flows that are unavailable in the implemented CLI or supported runtime API.
<!-- AC:END -->

## Definition of Done
<!-- DOD:BEGIN -->
- [ ] #1 Typecheck passes with no errors.
- [ ] #2 Linter passes clean.
- [ ] #3 Tests are added for the change and the full suite is green.
- [ ] #4 Public functions and exported types are documented.
- [ ] #5 No dead code or unused exports are introduced.
- [ ] #6 The core import-boundary holds: core depends only on ports, never on concrete adapters.
- [ ] #7 Runtime consumption coverage includes listing providers, inspecting one provider, seeing defaults with sources, and applying a capsule provider override.
- [ ] #8 Runtime override coverage rejects AuthProvider, ChannelAdapter, and SecretStore overrides through the capsule provider flow.
- [ ] #9 Runtime docs and help text are checked against the implemented command/API surface so stale command names are not introduced.
<!-- DOD:END -->
