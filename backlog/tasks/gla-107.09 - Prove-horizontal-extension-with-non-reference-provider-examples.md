## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Demonstrate that a provider can be added horizontally through the supported package, profile, and install path without narrow-waist edits.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 At least one non-reference provider or template package for a popular user-facing layer is selected through a provider profile or overlay.
- [ ] #2 The selected non-reference package appears in catalog, schema, skills or docs, doctor diagnostics, and dry-run admission with the same graph projection as reference providers.
- [ ] #3 The relevant runtime or dry-run path uses the selected non-reference package without provider-specific imports in app, gateway, session, identity, worker core, or kernel.
- [ ] #4 The extension example includes contract tests proving package validation, profile selection, compatibility, availability diagnostics, and redaction behavior.
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Depends on named profiles, security subcontracts, and author validation surfaces.
<!-- SECTION:NOTES:END -->

## Definition of Done
<!-- DOD:BEGIN -->
- [ ] #1 Typecheck passes with no errors.
- [ ] #2 Linter passes clean.
- [ ] #3 Tests are added for the change and the full suite is green.
- [ ] #4 Public functions and exported types are documented.
- [ ] #5 No dead code or unused exports are introduced.
- [ ] #6 The core import-boundary holds: core depends only on ports, never on concrete adapters.
