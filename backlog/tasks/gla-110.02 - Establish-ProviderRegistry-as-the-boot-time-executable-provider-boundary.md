## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Replace the caller-facing role of provider sets/modules with a boot-time registry boundary for executable provider metadata, factories, probes, and package evidence.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A booted app can enumerate registered provider manifests, versions, factory availability, probe metadata, and package evidence through ProviderRegistry without receiving AppProviderSet as its provider-discovery object.
- [ ] #2 Registry population fails closed with diagnostics for duplicate provider ids, duplicate provider id/version pairs, duplicate template ids, and unknown compatibility relation keys before catalog or admission resolution can use the data.
- [ ] #3 Provider creation through the registry preserves both synchronous and asynchronous provider factories, and unsupported call sites receive an explicit async-unsupported diagnostic instead of silently projecting the provider unavailable.
- [ ] #4 Provider registration after the registry is sealed is rejected with a deterministic diagnostic, so runtime capsule admission cannot mutate executable provider code.
- [ ] #5 Code outside the registry compatibility boundary no longer discovers executable providers by reading provider-set modules.
<!-- AC:END -->

## Definition of Done
<!-- DOD:BEGIN -->
- [ ] #1 Typecheck passes with no errors.
- [ ] #2 Linter passes clean.
- [ ] #3 Tests are added for the change and the full suite is green.
- [ ] #4 Public functions and exported types are documented.

- [ ] #8 At least one reference provider package boots through the registry path without using AppProviderSet as the provider-discovery object.
- [ ] #9 Public registry types or API docs identify the supported registration, enumeration, creation, and sealing contracts.
