## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Replace the caller-facing role of provider sets/modules with a boot-time registry boundary for executable provider metadata, factories, probes, and package evidence.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 A booted app can enumerate registered provider manifests, versions, factory availability, probe metadata, and package evidence through ProviderRegistry without receiving AppProviderSet as its provider-discovery object.
- [x] #2 Registry population fails closed with diagnostics for duplicate provider ids, duplicate provider id/version pairs, duplicate template ids, and unknown compatibility relation keys before catalog or admission resolution can use the data.
- [x] #3 Provider creation through the registry preserves both synchronous and asynchronous provider factories, and unsupported call sites receive an explicit async-unsupported diagnostic instead of silently projecting the provider unavailable.
- [x] #4 Provider registration after the registry is sealed is rejected with a deterministic diagnostic, so runtime capsule admission cannot mutate executable provider code.
- [x] #5 Code outside the registry compatibility boundary no longer discovers executable providers by reading provider-set modules.
<!-- AC:END -->
