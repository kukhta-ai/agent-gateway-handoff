## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Make capsule provider defaults and compatibility requirements belong to templates and assembly specs instead of broad runtime profiles.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 Template package scaffolding emits consumed default-provider fields and consumed compatibility fields for capsule provider families, so a scaffolded package affects resolution without manual schema repair.
- [x] #2 Capsule template resolution uses provider-id defaults and provider-specific config from the template, user overrides, and registry/catalog data without mutating a global browser-handoff template from a broad profile.
- [x] #3 Assembly inputs can express Launcher, Workspace, HumanEntrypoint, AgentConnector, and CompletionDetector selections in a stable serialized shape that does not include app infrastructure providers.
- [x] #4 Compatibility ambiguity, missing-provider, and required-part diagnostics use the same template fields for scaffolded packages and hand-authored packages.
- [x] #5 Existing CLI session creation and reference templates resolve to the same observable default capsule providers after the migration.
<!-- AC:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Final summary: capsule provider defaults are now resolved through TemplatePackage/defaults and graph projection; AssemblySpec validation rejects app-infrastructure provider selections before CLI projection; existing reference/default session behavior is preserved. Full pnpm gate green and independent re-review approved.
<!-- SECTION:NOTES:END -->
