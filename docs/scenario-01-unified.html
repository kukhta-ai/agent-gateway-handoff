The provider stack — what's pluggable on every layer

Every capability GLA leans on a third party for is a pluggable provider: a catalog kind with a concrete dependency behind it (see 02-provider-and-extension-model.md). Swapping any one is "install a different provider plugin" — the rest of the system, and the agent's gla commands, are unchanged. This slice's concrete choices, layer by layer:

Not pluggable here

GLA core (our code, not a dependency): Admission + Policy (Cedar is the embedded policy engine), the Task / Session / Capability / Route / Completion services, and the Worker plane — these appear as their own lanes in the diagram but carry no provider marker, because they are not swappable dependencies. External (not a GLA dependency at all): the agent runtime (Hermes), the website (acme.example), and the user's email inbox.

The lanes

Actors & externals

  • User — the human, in Telegram and at their laptop
  • Authenticator — WebAuthn passkey / fingerprint, used at enrollment (Phase E) and every handoff
  • Telegram — channel · ChannelAdapter
  • Website — acme.example (third party)
  • Email — the user's inbox (third party)

Agent

  • Hermes — the using agent; drives via gla

Edges & providers

  • gla CLI — the Agent Bridge surface
  • Gateway · Caddy — verify grant + proxy
  • Auth · authentik — WebAuthn step-up

Control plane (GLA core · not pluggable)

  • Admission · Cedar — mutate → validate the proposal
  • Task svc — the multi-step aggregate
  • Session svc — the per-handoff aggregate + saga
  • Capability svc — mint / revoke macaroons
  • Route ctrl — mount / unmount gateway routes
  • Completion svc — validate + normalize the done-signal

Worker & capsule

  • Worker · Docker — spawner / launcher (tier T4)
  • Capsule — Chromium · noVNC entrypoint · CDP connector

The agent's command sequence

Every control step above, as the concrete gla calls in order. Lines marked (CDP) are the agent driving the live capsule with its own tooling against the connector — not the CLI.

# precondition (one-time, operator-run, not an agent command): recipient enrolled — see Phase E
gla whoami
gla template show browser-handoff
gla skill show browser-handoff
# task is optional — a single-capsule goal may skip it (implicit task)
TASK=$(gla task create --intent "register on acme" --recipient $USER --fields task_id -q)
gla session create --task $TASK -f assembly.json --dry-run     # admission check only
SESS=$(gla session create --task $TASK -f assembly.json)       # provisions the capsule
#   -> {session_id, connector={cdp_url, secret_ref}}
# (CDP) drive Chromium via the connector: open acme.example, go to /register
H1=$(gla handoff open --session $SESS --reason "complete registration form" --fields handoff_id -q)
gla handoff wait $H1 --timeout 15m                             # blocks -> {status=submitted}
# (CDP) read /verify -> "code emailed"
H2=$(gla handoff open --session $SESS --reason "enter verification code" --fields handoff_id -q)
gla handoff wait $H2 --timeout 15m                             # blocks -> {status=verified}
# (CDP) configure the account on /dashboard
gla task complete $TASK                                        # tears down capsule, revokes caps

Reading this as an extension surface

Every bold provider in the stack table is a row the operator can change by installing a different plugin — Docker → Firecracker, Telegram → Slack, noVNC → KasmVNC, authentik → Authelia — with no change to the gla commands the agent runs and no change to GLA core. That is the inversion-of-control model in 02-provider-and-extension-model.md: the agent composes registered providers by capability; the concrete dependency behind each capability is the operator's choice, discovered at runtime through the catalog.
