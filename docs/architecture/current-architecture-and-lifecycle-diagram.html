GLA Current Architecture And Lifecycle

Current implemented shape after the provider-host/provider-graph work: a narrow runtime core, a typed provider graph, trusted provider sets, CLI/MCP agent surfaces, one public gateway, and temporary two-actor capsules, with provider authoring feeding trusted install-time packages.

Component Architecture

Solid arrows are runtime control/data flow. Dashed arrows are install-time or read-only evidence flow. The agent can inspect and consume providers through the catalog; executable provider registration happens only through trusted provider packages installed into provider sets at app boot.

Provider Creation Flow

This is the horizontal-extension path for adding a provider to an existing layer. The authoring UX and installation UX are separate even when the same physical agent on the same VPS performs both jobs.

1. Author chooses layer
Pick targetAuth, channel, runtime, surface, completion, or secret store.
Read contractLayer interface, manifest schema, config schema, state namespace.
Check fitRequired open parts and compatible provider relations.
2. Build package
ScaffoldCreate manifest, package metadata, tests, and examples.
ImplementProvider factory, probes, assets, templates, or bindings.
DefaultsDeclare profile defaults by provider id.
RelationsDeclare required parts and compatibility.
EvidenceKeep WPM binding and dependency proof inputs with the package.
3. Validate locally
SchemaManifest, defaults, relations, templates, and config validate fail-closed.
Graph dry runDuplicate ids, duplicate versions, missing providers, and typos reject.
Runtime testsFactories, probes, assets, and handoff surfaces are exercised.
InspectDiagnostics show what the catalog will consume before install.
4. Install or publish
Trust decisionOperator reviews source, package, evidence, and blast radius.
PinWPM installs the package and records host evidence.
Provider setTrusted distribution exposes manifests and modules at app boot.
RecordInstall receipts and redacted diagnostics become audit evidence.
5. Consume at runtime
Catalog graphProvider, template, defaults, compatibility, and availability appear together.
AdmissionProfiles and proposals resolve against the updated graph.
Provider HostFactories create runtime ports only after graph and policy pass.
User-facing UXAgent can discover and select the new provider through catalog/profile flows.

Runtime Lifecycle

Scenario-01 lifecycle from enrollment through teardown. The same session can open multiple handoff windows onto the same capsule; teardown is the terminal cleanup path.

0. Precondition
Provider profileSelect defaults and config overlays.
Install evidenceWPM receipts and probes prove dependencies.
Enroll recipientIdentity/Auth binds credential to recipient.
InvariantNo handoff verifies an unenrolled recipient.
1. Agent orient
ConnectAgent enters through CLI or MCP bridge.
AnchorBridge mints agent-authority capability.
DiscoverCatalog returns providers, templates, schemas, skills.
Read-onlyAgent can inspect graph, never register code.
2. Propose
AssembleAgent submits a concrete session proposal or dry-run.
Resolve graphTemplate defaults pick provider subgraph.
AdmissionMutate defaults, validate policy, compatibility, config.
Fail closedUnknown, unavailable, or incompatible nodes reject.
3. Provision
Provider HostCreate selected runtime ports from factories.
SessionCreate session aggregate and capability lineage.
WorkerLauncher spawns capsule with workspace and connector.
EvidenceAudit records decisions, redacted diagnostics, state.
4. Agent drive
ConnectorAgent drives capsule through CDP or another connector.
Capsule stateAgent and human surfaces share scoped runtime state.
Agent blindRaw user secrets never enter agent path.
5. Open handoff
Requesthandoff open names the live session.
Mint grantRecipient-bound, scoped, short TTL capability.
Mount routeRoute controller programs gateway path.
DeliverChannel sends link to exactly the bound recipient.
GatewayOnly public door for the human.
6. Verify and act
Open linkUser reaches Access Gateway, not capsule directly.
VerifyGrant, recipient caveat, TTL, revocation, assurance.
ProxyAuthorized WS reaches human entrypoint, such as noVNC.
Wait/live-driveAgent may wait or drive the connector in parallel.
7. Complete
Detector firesURL watcher or user-done emits signal.
NormalizeCompletion service validates and returns envelope.
ResumeBridge returns result to agent.
Re-open optionalSame capsule can get another window.

RevokeCapability service revokes descendants.
UnmountGateway route and live WS are closed.
ReapCapsule stops, workspace/profile cleanup runs.
Close auditNo orphan capsule, no live grant, no residual route.

Load-Bearing Rules

These are the constraints the diagram assumes. They are the current architecture boundaries, not UI suggestions.

Provider defaults are ordinary packages

Defaults live in a selected provider profile inside a trusted provider set. Generic app composition receives provider ids and config; it does not hard-code the reference default choices.

Provider graph is the read model

Catalog, admission, doctor, and CLI/schema output consume projections of the same graph: manifests, profiles, compatibility, WPM evidence, probes, config schemas, and skills.

Provider Host owns runtime factories

Trusted provider modules register factories at boot. Runtime agents can inspect and consume the result, but cannot register executable provider code.

Access Gateway is the only public door

User traffic always transits grant verification, recipient binding, revocation, and assurance checks before it can reach a capsule entrypoint.

Agent Bridge is unprivileged

The agent enters through CLI/MCP and gets capabilities, read models, and completion envelopes. It never gets raw secrets, gateway admin authority, or host control paths.

WPM satisfies host dependencies

GLA declares dependency needs. WPM performs host-specific install/adopt/verify work and leaves receipts that become graph availability evidence.
