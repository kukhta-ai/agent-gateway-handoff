Provider Layer Refactor - AS IS / TO BE

Proposal for a large architecture cleanup that removes unneeded provider-layer entities and gives each surviving entity one job. This deliberately treats current provider architecture docs as historical context; the AS IS side is grounded in the current implementation shape.

Refactor Thesis

The core problem is not that the app has too few abstractions. It has several abstractions whose responsibilities are smeared across each other. The target is fewer architectural nouns, not a larger provider framework.

Eliminate

Broad provider set/profile as product concepts

Remove AppProviderSet as a central entity and remove the broad ProviderSelectionProfile that selects app infrastructure and capsule parts together.

Create

ProviderRegistry as the executable registry

Boot code registers trusted provider packages into one registry. The registry owns provider ids, families, descriptors, factories, probes, schemas, asset descriptors, and state namespaces.

Create

AppDeploymentConfig for app infrastructure

Auth, channel, secret store, and other daemon-level selections are app boot configuration. They are not capsule composition and should not live in capsule templates.

Narrow

Capsule templates own capsule defaults

Launcher, workspace, entrypoint, connector, and completion detector choices belong to CapsuleTemplate defaults/fixed/open parts and to AssemblySpec overrides.

AS IS: Flattened Provider Layer

Current code path: AppProviderSet carries modules, named profile manifests, selected profile id, runtime profile, default config, default services, client assets, and template probes. requireSelectedProfile() merges those inputs before both app infrastructure and capsule runtime creation use the same broad profile.

TO BE: One Entity Per Responsibility

Target code path: the composition root registers trusted packages, app deployment config selects only daemon infrastructure, capsule templates own capsule defaults, catalog is a read model, and admission is the only place that turns a request into a resolved capsule graph.

Elimination Plan

The goal is not a rename-only cleanup. Each row removes a responsibility overlap and leaves one owner.

AppProviderSet Combines trusted module supply, profile catalog, active profile, defaults, services, assets, and probes. CompositionRoot + ProviderRegistry + explicit config objects Eliminate as central architecture entity. Replace with boot registration functions or a thin distribution module.

Refactor Sequence

This should be a strangler refactor. Add the target owners first, route existing behavior through compatibility adapters, then delete the broad entities when tests prove parity.

1. Introduce ProviderRegistry

Add an explicit registry API and make reference providers register into it. Keep ProviderHost as an adapter until callers move.

2. Extract AppDeploymentConfig

Move auth, channel, and secret store choices out of the broad profile. Preserve current flags/env by adapting them into the new config shape.

3. Move capsule defaults to templates

Make CapsuleTemplate the authority for fixed/default/open capsule parts. Remove profile mutation from template construction.

4. Rebuild CapabilityCatalog inputs

Build the read model from registry descriptors, app config, template packages, WPM evidence, and probes. Catalog remains read-only.

5. Update admission and provisioning

Admission resolves AssemblySpec only against template-open capsule choices. Runtime creation asks the registry for factories after admission.

6. Delete compatibility layer

Remove AppProviderSet, broad ProviderSelectionProfile, selected profile id, and provider-set callback seams after all CLI, doctor, and E2E paths use the new owners.
